# Bindings

Bindings are host functions that guest code is allowed to call. They are the
only supported way for source running in the sandbox to interact with your
application or the systems connected to it.

A binding should represent a focused capability. Instead of exposing a
database client, for example, the host can expose a function that loads one
kind of record after applying the application's validation and authorization
rules.

## Defining bindings

Bindings are defined under a namespace. The namespace becomes a global object
in the sandbox, and each binding becomes a method on that object.

```ts
import { run } from 'run';

const result = await run({
  source: `
    const user = await users.find("user_123");
    return user;
  `,
  bindings: {
    users: {
      find: async (id: string) => {
        return { id, name: 'Ada' };
      },
    },
  },
});
```

The complete name of the binding in this example is `users.find`. The `users`
namespace is available only for this invocation.

A namespace must be a valid JavaScript identifier, must not conflict with a
reserved global, and must not begin with `__run`.

## Calls

Calling a binding creates a request from the guest to the host. The arguments
are serialized, copied to the host, and passed to the binding as ordinary
function arguments. The returned value is then serialized and copied back to
the guest.

Bindings may return values directly or return promises:

```ts
const bindings = {
  math: {
    double: (value: number) => value * 2,
  },
  users: {
    find: async (id: string) => {
      return { id, name: 'Ada' };
    },
  },
};
```

Guest code should await every binding call. Returning while binding work is
still pending can fail the invocation because the runtime cannot safely detach
host work from the guest that requested it.

```ts
await events.record({ name: 'opened' });
return { recorded: true };
```

Several binding calls can run concurrently when the guest awaits them
together:

```ts
const [profile, orders] = await Promise.all([
  users.profile(userId),
  orders.list(userId),
]);
```

The invocation limits both the total number of binding calls and the number
that may be in flight at once.

## Context

A binding has the option to call `getBindingContext()` to access information about its active
request:

```ts
import { getBindingContext } from 'run';

const bindings = {
  users: {
    find: async (id: string) => {
      const context = getBindingContext();

      return {
        id,
        logicalRunId: context.logicalRunId,
        name: 'Ada',
      };
    },
  },
};
```

`getBindingContext()` exposes the following information and controls:

- `abortSignal` lets the binding stop its work when the run is cancelled, times
  out, or fails.
- `invocationId` identifies the current execution attempt. It changes when an
  interrupted run is replayed.
- `logicalRunId` identifies the complete workflow and remains stable across
  replay attempts.
- `requestId` identifies the current binding call within the invocation.
- `requestIndex` contains the one-based order of the binding call.
- `bindingName` contains the complete binding name, such as `users.find`.
- `interrupt(payload)` pauses the run and returns an application-defined
  payload to the host.
- `resume` is available when an interrupted binding is invoked again. It
  contains the interruption ID, original payload, and supplied resolution.

These identifiers are useful for tracing, auditing, and deduplicating external
side effects. They are not authentication credentials. We will dive deep into these
later.

## Cancellation

The binding context includes an `AbortSignal`. It becomes aborted when the
invocation is cancelled, times out, or otherwise fails.

Bindings should pass this signal to operations that support cancellation:

```ts
const bindings = {
  search: {
    query: async (query: string) => {
      const { abortSignal } = getBindingContext();

      return searchClient.query(query, {
        signal: abortSignal,
      });
    },
  },
};
```

Aborting the signal cannot automatically undo work that has already completed.
Bindings that perform writes should use application-level idempotency and
deduplication.

## Failures

When a binding throws, its guest-side promise rejects. Guest code may catch the
error and continue:

```ts
try {
  return await inventory.reserve('item_123');
} catch (error) {
  return {
    reserved: false,
    message: error.message,
  };
}
```

The guest receives a sanitized error without the host stack or private
diagnostic details. The host should record the complete error before rethrowing
it when those diagnostics are needed.

Bindings are trusted code. They should validate every argument, enforce
authorization in the host, and return only the data required by the source.
