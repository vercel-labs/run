# Execution

An invocation includes more than evaluating the source. It begins when the host
calls `run()` and ends only after the result has been transferred, the run has
been interrupted, or an error has been reported.

The timeout and resource limits apply to this complete lifecycle.

## Preparation

The host starts an invocation by providing source and any bindings, limits,
cancellation signal, or continuation data that the run requires.

Before starting QuickJS, the package validates the binding names, checks that
every binding is a function, merges the configured limits, checks the source
size, and removes supported TypeScript syntax.

When a runner was created with shared limits, limits passed to an individual
invocation take precedence:

```ts
const runner = createRunner({
  limits: {
    timeoutMs: 30_000,
    maxResultBytes: 1024 * 1024,
  },
});

const result = await runner.run({
  source,
  limits: {
    timeoutMs: 5_000,
  },
});
```

This invocation has a five-second timeout and retains the runner's one-mebibyte
result limit.

## Workers

The package uses a process-wide pool of Node.js worker threads. An invocation
can reuse an available worker or create another worker when the process-wide
limit and available memory allow it.

The worker creates a new QuickJS context for the invocation, applies its memory
and stack limits, installs the hardened runtime and bindings, and evaluates the
source.

Only one invocation runs in a worker at a time. When the process-wide worker
cap has already been reached, the new invocation fails immediately with a
concurrency error rather than waiting in a queue.

The default worker cap adapts to the memory available to the process. It always
allows at least one invocation and does not exceed 32 active workers unless the
host configures a different cap.

## Limits

The default timeout is 30 seconds. The default memory limit is 64 MiB, and the
default stack limit is 2 MiB.

The source may contain up to 256 KiB. The final result may contain up to 1 MiB,
and guest console output may contain up to 64 KiB.

One binding call may send up to 1 MiB of arguments and return up to 4 MiB of
output. An invocation may make up to 256 binding calls, with no more than 32
calls in flight at once. Continuation state may contain up to 32 MiB.

These limits can be changed for a runner or an individual invocation. Every
configured limit must be a positive integer.

## Cancellation

An invocation can be cancelled with a standard `AbortSignal`:

```ts
const controller = new AbortController();

const pending = run({
  source,
  abortSignal: controller.signal,
});

controller.abort();

await pending;
```

Cancellation rejects the invocation with `RunAbortedError`. The same
cancellation state is propagated to active bindings through their binding
context and to continuation operations.

A timeout rejects with `RunTimeoutError`. The timeout includes time spent
executing guest code, waiting for host bindings, and encoding or decoding a
continuation.

Cancellation cannot undo host work that has already completed. Bindings that
perform side effects must account for that possibility.

## Completion

When the source returns a serializable value, the invocation resolves with a
completed result:

```ts
{
  status: 'completed',
  value: 42
}
```

The generic output type supplied to `run()` describes the expected value to
TypeScript, but it does not validate the runtime value.

When a binding pauses the workflow for an external decision, the invocation
resolves with an interrupted result:

```ts
{
  status: 'interrupted',
  interruptions: [/* ... */],
  continuation: '...'
}
```

There is no failed result status. Invalid input, uncaught guest exceptions,
timeouts, cancellation, protocol failures, and resource-limit violations reject
the invocation.

A binding exception initially becomes a rejected promise inside the guest. The
invocation can continue when guest code catches that rejection. Otherwise, the
error escapes the source and rejects the invocation.

## Cleanup

The QuickJS context is disposed after every outcome, including completion,
interruption, and failure. Guest globals and values cannot survive this
cleanup.

A healthy worker may then return to the pool for another invocation. A worker
that timed out, was cancelled, or encountered certain runtime failures is
destroyed instead.

This distinction is important: every invocation receives a fresh execution
context, but it does not necessarily receive a newly created worker thread.
